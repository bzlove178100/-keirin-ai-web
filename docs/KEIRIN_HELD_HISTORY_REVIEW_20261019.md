# 保留確認・誤申告訂正（合成レビュー専用・未公開候補）

Draft #266、基準main `d069ab9b6adcf9585954a5bae7be7df0546e473c`。
`ml.held_history_review` は、保留を確認した記録と根拠を保存し、誤った状態申告を訂正した
合成ケースだけ、元の確率表を使って再評価する。元の保留履歴を削除・上書きしない。

## 2つの判断

| decision | 必要な根拠 | レポート内の扱い |
| --- | --- | --- |
| confirm_nonstandard | 元の同着/欠車/中止と一致する合成結果。欠車車番も一致 | confirmed_excluded。確認完了、評価対象外を維持 |
| correct_declaration | 状態の誤申告であり、通常結果であることを示す合成結果と訂正理由 | 全保留の確認・競合検査に合格したレースだけreleased_for_synthetic_review |

実際の同着・欠車・中止を単一勝者へ変換する機能ではない。誤申告の訂正は明示操作であり、
通常結果を後から追加しただけでは解除しない。現在は生成した合成入力だけが対象。
実データの利用可否・実レース結果の真正性・ユーザーの公開/配備承認とは別の契約である。

## 必須入力

各確認記録は、既存の有効な `phase32-held-history-v1` または `ml-held-history-v1` 1件、
根拠 `synthetic-result-evidence-v1`、判断の3入力から作る。全処理で明示的なsynthetic指定が必須。
元schemaの完全検査に加え、日付/会場/番号・予定発走・7/9車の車番構成を厳密照合する。
選手本人IDはML snapshotにないため照合しない。会場の別名解決や推測は行わない。

根拠のキーは以下だけを受け付ける。

```json
{
  "schema_version": "synthetic-result-evidence-v1",
  "evidence_scope": "synthetic_test_only",
  "fixture_id": "generated-result-case",
  "race_identity": {"date": "2026-10-17", "venue": "SYNTHETIC", "race_number": 7},
  "scheduled_start": "2026-10-17T11:00:00+09:00",
  "car_numbers": [1, 2, 3, 4, 5, 6, 7],
  "result": {
    "result_status": "normal", "result_timestamp": "2026-10-17T02:20:00Z",
    "outcome_combo": "1-2-3", "settlement_odds": 40
  }
}
```

上記は生成fixture用の例。実データや別レースへ流用しない。
非標準確認ではresultを元のstatusとresult_timestampだけにし、withdrawnのみ元と同じwithdrawn_car_numbersを加える。
勝者・oddsを同時に渡すことや、余分なキー、boolの車番/odds、未知statusは拒否する。
根拠の結果確認時刻は元の保留確認時刻以降。normal/dead_heatは予定発走以降。

判断は `decision`、timezone付き `reviewed_at`、`reviewer_id`、空でない `reason` の4キー。
reviewed_atは根拠の結果確認以降。reviewer_idは `synthetic-`、fixture_idは `generated-` で始まる識別子。
識別子・理由・根拠は申告値であり、本人認証・第三者の確認・許諾を証明しない。

## 記録と競合規則

`held-history-review-v1` は元履歴・根拠・判断をすべてコピーし、元履歴と根拠のSHA-256を保持する。
validate_reviewは全体を再生成して厳密比較する。変更したフラグ・余分なキーも拒否する。
確認記録単独ではhold_released/evaluation_eligible=false。解除要求は一括検査に渡す。
digestは署名ではなく、入力全体を作り直せる者への改ざん防止を保証しない。

一括評価は `held_records` と `reviews` の2配列だけを受ける。通常履歴は受け付けない。
日付/会場/番号で両エンジンの保留を同じレースへまとめ、次の順で判定する。

1. 不正な元履歴/確認記録、入力に存在しない履歴を参照する確認記録は要求全体を拒否。
2. 同じレースの予定発走/車番構成の食い違い、1履歴への異なる確認記録、確認漏れはそのレースを未解決にする。
3. 訂正と非標準確認の混在、異なる訂正結果はそのレースを未解決にする。後日時刻による自動上書きなし。
4. 全件が非標準確認ならconfirmed_excluded。勝者・確率指標を作らない。
5. 全件が同一通常結果への訂正なら、エンジンごとに最新の保存予測を選ぶ。
   同じ保存時刻に異なるsnapshotがあれば、レース全体を未解決にする。
6. 合格レースだけ、その元確率表で固定予測の順位/log-loss/Brier等を計算する。
   Phase32とMLの指標は別集計。両者を混ぜた平均や金銭指標を作らない。

完全重複の履歴/確認記録は件数を増やさず、入力順でも選択を変えない。
訂正結果の時刻は同一時点のtimezone表記差を許し、oddsの40と40.0は同値とする。
新しい未確認の保留が同じ入力に加わった場合は、以前の訂正があっても再び評価対象外になる。
別レースの指標は影響を受けない。評価対象が0件なら指標nullで、0%として集計しない。

## オフラインCLI・保存

```sh
python -m ml.held_history_review create-review held.json evidence.json decision.json \
  --synthetic --output review.json
python -m ml.held_history_review evaluate batch.json \
  --synthetic --output review-report.json
```

出力は上書き不可。検証失敗では出力なし。評価対象0件では監査レポートを保存しexit 2を返す。
レポートは元履歴と確認記録を全件保持する。解除の効力はこの入力一式に対する合成レビュー内だけ。
履歴ファイルを省略した別入力や、未提供の別エンジン保留を横断検知する永続状態はない。
元履歴・根拠・確認記録を一緒に保存し、再開時には同じ入力一式で照合する。

通常履歴や学習データへのexportは設けない。既存のpartition_holds/evaluate_historiesは元保留を引き続き除外する。
学習/DB/外部取得/本番/金銭EV/昇格はOFF。snapshot・モデル・予測時odds・captureは不変。
公開Web/Edge、実owner認証下の訂正、実データ向け審査/権限/永続記録、通常収集経路への解除反映は未接続。

## ローカル操作画面と確認一式の保存

`python -m ml.synthetic_workbench --synthetic --port 8765` の
`http://127.0.0.1:8765/held-review` で利用する。合成予測画面のリンクからも開ける。
モデル学習を実行せず、この画面だけを起動できる。既存のloopback限定・Host/Origin・
X-Keirin-Local検査、script hash付きCSPを共有し、外部通信・任意ファイル配信は追加しない。

1. 有効な保留JSON（単体/配列）、保存した確認一式、または上記CLIのレポートを選び「検証して追加」。
2. 対象保留と、別途生成した `synthetic-result-evidence-v1` のJSONを選ぶ。
3. 除外維持/誤申告訂正、確認者ID・確認日時・理由を入力して判断を追加する。
4. 未確認/競合を解消した入力だけが合成レビュー内で評価される。元保留は変更されない。
5. 一時保存の場合は終了前に「確認一式をダウンロード」し、ブラウザの保存結果を確認する。
   自動保存が有効なら同じ保存先で再起動する。手動バックアップの追加読込も利用できる。

保存形式は `synthetic-held-review-bundle-v1` payloadとそのSHA-256のenvelope。
payloadはschema_version、synthetic_only=true、held_records、reviewsだけを持つ。
元履歴・根拠・判断を含めて保存し、読込時はdigestだけでなく全履歴/確認記録を再検証する。
CLIレポートも再計算した全体との一致を要求する。不正な1件が混ざる場合は要求全体を拒否し、
現在の記録を保持する。完全重複は追加しない。部分一式を読んでも既存の保留や競合判断は消さない。
別タブが先に記録を変えた場合はrevision不一致で409を返し、最新状態へ戻して再選択を求める。

上限は保留20件・確認40件、保存一式32 MiB。根拠ファイルは3 KiBまで、判断POSTは8192 bytesまで。
ファイルのJSONをブラウザで再構成せず、元文字列として送りサーバーで解釈する。
40.0→40等の表記変換による元履歴/digestの変化を防ぐ。保存済みの最大一式も再読込できるよう、
読込POSTは文字列escapeの最大2倍とenvelope分を含む64 MiB+1024 bytesまで。解釈前の元文字列は32 MiBまで。
レース番号は既存の連携契約どおり1〜12。古い合成予測セッションのseries繰上げで生じる17R/19R等は
この画面では拒否する。番号や予定時刻を推測修正しない。

保存先を指定しない場合はサーバーメモリだけに保持され、プロセス終了で失われる。
`--state-dir` を指定した場合は確認一式も自動保存する。画面で一時保存/自動保存/復元/保存失敗を区別する。
読み込まなかった保留の存在や、保存しなかった後続の判断は検出できない。
ローカル合成入力の保存経路であり、実データ向け永続台帳・クラウド同期・スマホ公開ではない。

## 自動保存と中断復旧（2026-10-20）

起動時に `--state-dir /absolute/path/outside/repository` を追加する。
既存の予測セッションは同じ保存先の `synthetic-session.json` を引き続き使い、確認一式は
`held-review/held-review.json` に別保存する。既存v1セッションを移行・書換えせず利用できる。
同じ保存先を指定して再起動すると、digestと全履歴/根拠/判断を検証し、元の固定予測からレポートを再計算する。
保留・確認記録とレポート内の監査配列を同じ安定順序で保持し、復元前後の内容を一致させる。
フォームの未送信入力は保存対象外。成功応答を受けた読込/判断の一式が保存対象。

保存は既存SessionStoreのファイル処理を共有する。固定名、単一POSIXプロセスの協調ロック、
32 MiB上限、symlink/非通常ファイル/複数hardlinkの拒否、外部変更の比較を維持。
一時ファイルをflush/fsyncし、同じディレクトリ内で置換し、ディレクトリをfsyncしてからメモリへ反映する。
保存成功前に200や「自動保存しました」を返さない。確認一式の保存から予測モデルの学習は呼ばない。

置換前の保存失敗では元ファイルと確認済みメモリを保持。置換後の同期失敗ではディスク上の結果が不確実なので、
503とwrite_blockedを返し、追加操作を止める。画面とダウンロードは直前に確認できたメモリ状態であると表示する。
再起動時に実ファイルを再検証するまで書込再開しない。外部変更も上書きしない。
破損ファイルでは起動を拒否し、空状態への置換や一時ファイルの自動昇格はしない。
正常ファイルがない場合の孤立partialは成功済み保存とみなさない。

保存先の選び間違い、ファイル削除、過去の有効ファイルへの手動差戻し、未提供の別作業記録を検出する
グローバル台帳や署名はない。任意の本番ファイルシステム・電源断・複数ホストへの耐久性保証でもない。
検証はローカルPOSIXの実ファイル、SIGKILLによるプロセス終了、注入したI/O障害の範囲。

## 同じ合成セッションから直接追加（2026-10-20）

確認画面の「予測画面の保留を再確認」で、同じサーバーが保持するML保留を一覧表示する。
「表示した保留を一括追加」で、JSONダウンロード/ファイル選択を挟まず既存の確認一式へ追加する。
確認画面を開いただけでは追加せず、通常結果と未確定予測は対象にしない。別エンジンの保留や
根拠JSONは引き続き個別に読み込む。根拠・判断を自動生成せず、訂正や通常履歴への解除もしない。

サーバー側で合成セッション全体、予測と結果の対応、全保留の確認用契約を再検証する。
ブラウザからは確認一式のrevisionと表示した元保留一式のsource_revisionだけを送る。
同じlock内で両方を照合し、別画面で元保留が増えた場合や確認記録が変わった場合は409で停止。
最新状態を表示して明示的な再追加を求める。新しい保留を後から作っても自動同期はしない。
確認画面の「追加済み」件数は、現在のセッションにある保留との完全一致件数である。

既存load/checkpoint経路を再利用し、重複排除・既存判断/競合保持・上限・保存失敗時503を維持。
元予測セッションは書き換えず、確認一式だけを自動保存する。Pythonの元値を直接渡すためfloat表記を失わない。
元予測の保存失敗中、入力不正、上限超過は全体を拒否する。旧セッションの17R/19R等も従来どおり拒否し、
正しい保留だけの部分追加や番号の推測訂正はしない。既存ファイル読込と手動バックアップは維持。
この経路は現在のプロセスが保持する合成入力専用。別サーバー/別保存先の存在や改変を横断検知しない。
